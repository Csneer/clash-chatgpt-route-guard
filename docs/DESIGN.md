# 设计与安全边界

## 状态路径

定时器每约 30 秒启动一次 oneshot 服务。自动 `check` 调用 `clash_demand.run`：

```text
本地成功记录/错误日志/journal
              │
              ├─ 不可读、空闲、成功、阈值不足 ──> 本地状态，零外部请求
              │
              └─ 多个新的网络失败
                    │
                    ├─ 冷却/预算/保护期/锁检查
                    ├─ 一次真实业务确认
                    ├─ 多轮确认仍失败
                    ├─ 隔离全候选评估
                    ├─ 目标复测 + 切前复测
                    └─ 事务切换 + 切后复测；失败最多回退一次
```

成功调用不会形成“守护器自己的健康请求”。Clash journal 只提供诊断上下文，不能单独授权外部请求，也不会让守护器探测产生的日志反过来触发下一轮。

## 默认保守阈值

- 15 分钟证据窗口内至少 3 个不同请求，失败首尾至少 2 分钟。
- 诊断轮之间至少 10 分钟，24 小时最多 6 轮。
- 至少 3 轮失败且跨度至少 20 分钟才允许候选扫描。
- 24 小时最多 2 次自动切换尝试和 2 轮全量评估。
- 同出口样本只在事件期间采集，有效期 30 分钟。

这些数字是防止无意义换 IP 的默认值，不是可用性 SLA。实时长连接没有终止日志时，守护器无法凭空推断其状态。

## 事务安全

切换前保存 pending WAL，再通过控制器修改受管理选择器。切换后检查选择器、依赖图、配置并重新执行业务检查；检查失败尝试恢复原选择。检测到第三方同时修改或无法确认恢复时保留 pending，后续自动操作停止，要求人工核查。

候选使用临时 Mihomo 和回环监听，不把每个候选写入生产配置。候选图只接受静态 YAML 中定义的协议和明确的 select/dialer-proxy 依赖，复杂外部资源默认跳过。

## Clash 运行模式

守护器在每次 timer 检查中通过控制器只读 `/configs`，跟随 Clash 当前的 `global` 或 `rule` 模式；它不会向 `/configs` 写入，也不负责选择模式。界面切换模式后无需重启守护服务，运行时模式不要求与 YAML 中的启动模式相同。`direct` 等不支持的模式或控制器不可用时暂停自动探测与选择；恢复后重新建立证据并进入保护期。

在 `global` 模式下，受管理选择器是 Mihomo 内置的 `GLOBAL`，候选来自该选择器的运行时显式成员。很多 Clash Verge 生成的 YAML 没有静态 `GLOBAL` 组，这时选择只通过 `/proxies/GLOBAL` 和 Mihomo 的 `profile.store-selected` 运行时缓存完成，守护器不会改写生成 YAML。

内置 `GLOBAL` 的事务要求 Clash 配置已启用 `profile.store-selected: true`；缓存被删除或管理工具覆盖选择时不能保证重启后保留。`GLOBAL` 的切换影响所有经过该选择器的流量。守护器不会修改系统 Wi-Fi/有线路由，也不会在 global 模式下恢复规则分流。

在 `rule` 模式下，业务 URL 的第一条匹配规则必须进入 `entry`，该入口沿途必须落到配置的 `selector`；规则、运行时规则和依赖图仍会严格核对。快照包含所有手动选择器（包括 `GLOBAL`）的当前选择，避免遗漏业务链或候选依赖变化。

模式、选择器、配置或人工选择变化时，旧失败证据、出口样本和检查结果会清空，并进入保护期。评估或事务期间发现模式变化会取消后续操作；未完成 WAL 会保留给人工核查。守护器从不替用户把 `global` 切成 `rule`，也不会把 `url-test` 当作稳定出口。

控制器没有提供“仅在模式未变时更新选择器”的原子条件写入；守护器在写入前后复核模式并在检测到变化时停止回退，不能保证覆盖两次检查之间极短的模式往返。订阅或 GUI 更新生成配置仍须遵守共享锁及选择持久化约定。

`mode: observe` 可以发起显式检查但不做自动事务；`mode: auto` 仍必须配合 `activity.strategy: faults-only`。配置中关闭 activity 后，CLI 的自动 `check` 直接拒绝，防止意外恢复旧的周期轮询。
